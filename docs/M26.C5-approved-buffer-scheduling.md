## What changes for the user

Today has a publishing card beside the existing research/Brief workbench:

1. Choose a saved X/LinkedIn draft. The initial selection prefers a draft that
   already passes deterministic publishing checks, but never rewrites it.
2. Connect the user's own Buffer through OAuth, then explicitly finish the
   connection for the same signed-in PostBeacon owner. Connection alone cannot post.
3. Choose one verified destination and an explicit UTC time 10 minutes–30 days
   ahead. Prepare a preview, not an external post.
4. Read the **complete frozen copy, account, time and expiry**, then separately
   check consent and approve. Changed copy, facts, trial snapshot, account,
   connection revision, saved project version or time invalidate approval.
5. See an owner-scoped receipt. `scheduled` is not `published`; `unknown` means
   inspect Buffer, not blindly retry. Reading or returning to the page never sends.

The fictional demo exercises review, consent, invalidation and a scheduling
receipt with no network task, saved state, account connection or publication.
It includes a short, truth-checked single-post example; the existing longer
story remains available for manual editing/publishing.

## Deliberate pilot limits

- X and LinkedIn, one plain-text post and one approved product-entry link.
- No threads, images, bulk campaigns, replies, DMs, scraped contact lists,
  autonomous rewrites, automatic approval or unbounded posting authority.
- At most 20 prepared previews per user/UTC day, 5 send attempts per user and
  keyed Buffer account/day, 100 globally/day. Failed/uncertain attempts consume
  allowance. Read reconciliation: 100/user, 1,000/global/day, 30-second cooldown.
- Approval expires after at most 15 minutes and always before the scheduled
  instant minus two minutes. The server claims it atomically before the sole
  outbound scheduling attempt; a timeout/crash cannot reopen the old approval.
- Another preview after an autosave cannot duplicate an active identical
  body/destination/instant. Expired unsent approvals can be prepared afresh;
  their old consent is never revived.
- Channel metadata refresh and new OAuth starts share a 30-second database
  cooldown, including failed reads. Finish remains a one-time staged-code claim.
- Provider-reported sent status remains a separate receipt. This release does
  **not** create an experiment clock or import engagement metrics automatically.
- Buffer owns actual scheduled execution. No new high-frequency cron, 24-hour
  monitoring guarantee, autonomous outreach or exactly-once external-send claim.

## Architecture and trust boundaries

| Layer | Responsibility |
| --- | --- |
| `bufferPublishing.ts` | Strict commands, shared truth/editorial/link/size gates, schedule bounds, canonical approval hash. |
| `bufferConfig/Crypto/Connections/Provider` | Fail-closed setup, AES-256-GCM grants with owner/record/purpose AAD, public metadata projection, fixed OAuth/GraphQL endpoints. |
| `bufferConnectionServer.ts` | Owner-bound staged OAuth + PKCE, distributed single-use refresh serialization, metadata, disconnect. |
| `bufferPublishingServer/Provider` | Load canonical saved context; prepare, claim, one scheduling attempt, exact-provider-ID reconciliation. No LLM can supply arbitrary API queries or destinations. |
| Database RPCs | Owner-composite FKs, read-only owner RLS, private vault/state, revision/nonce/expiry fencing, atomic budgets and deletion locks. |
| `useBufferPublishing` / publishing card | Owner/project-scoped reads and explicit commands. Abort stale work, suppress double clicks; never treat local UI state as provider evidence. |

Existing Next Route Handlers, Supabase and native crypto are retained. No agent
framework, dependency, model, credential broker or ordinary model routing changes.

### Connection

OAuth uses `account:read posts:read posts:write offline_access`, PKCE S256, random
opaque state, ten-minute expiry, and a `__Host-` Secure/HttpOnly/SameSite=Lax cookie
with no Domain attribute. Start and callback use the canonical apex host, not
www. The callback only stages an encrypted code; bearer-authenticated finish
must match its original owner and browser binding. No code/token is reflected
in redirects, public errors, logs, project JSON, model input or browser responses.

Access and refresh grants live in a separate server-only vault. A database
lease serializes rotating, single-use refresh tokens across processes; an
ambiguous or expired lease requires reconnecting rather than reusing the token.
New OAuth rounds fence late work from old rounds. Provider reads are bounded
(four organizations, 100 supported channels, two concurrent organization reads,
12 seconds/request, 128 KiB response); disconnect/revision checks precede reads.

### Approval and observations

The server reads the owner’s saved project, current facts, voice, success
contract, trial provenance and exact post index. It does not accept a browser
body, success status or provider ID. The hash includes a server-generated nonce,
project timestamp, context/draft digest, account revision, channel and time.
Explicit UTC avoids pretending a local date/time can be converted reliably
across daylight-saving ambiguities.

Provider creation uses only one fixed `createPost` mutation in `customScheduled`
mode. GraphQL/HTTP ambiguity becomes `unknown`, not an automatic replacement.
Read-only reconciliation requires the recorded provider ID and the same keyed
Buffer-account identity, exact text/channel/service/schedule and plausible sent
time. Read nonces fence delayed observations; sent receipts cannot regress.

## Data rights and retention

- Owner export includes connection/channel metadata, full approval/delivery
  history and owner daily usage. It never queries grants or OAuth states, and
  excludes internal fence values and shared-account quota digests.
- A durable entitlement marker makes missing optional publishing tables fail
  export closed after first use. Pre-install, never-used accounts remain usable.
- Transactional deletion locks **projects → connections → children**, then wipes
  approvals, OAuth material, vaults, metadata, owner counters and the existing
  Agent/workspace data. Base-schema reruns retain this optional-table coverage.
- Project deletion/inactivity retention cascades delivery content. Account-wide
  grants persist until disconnect or account deletion, not project deletion.
- OAuth material becomes invalid after ten minutes; physical cleanup is the
  next enabled daily retention sweep. Daily owner/global and keyed, pseudonymous
  Buffer-account counters use the configured retention window (currently 30
  days). Shared counters survive account deletion to prevent allowance resets;
  they are **not called anonymous** and contain no text or credentials.
- Local disconnect/delete **cannot cancel Buffer-accepted queued posts**, delete
  external posts or claim to revoke Buffer's app grant. The UI instructs users
  to manage those in Buffer. Public notices change with configuration, while
  dormant integrations are not advertised as live.

## Mandatory installation and release order

Do not run SQL automatically on build/deploy. Production execution and credential
setup are separately authorized actions, not implied by code acceptance.

1. Prior C.4 blockers first: install `20261026_workspace_ownership.sql` and
   `20261026_atomic_usage.sql`; corresponding seven- and four-row audits must
   pass, along with base/Agent/mission audits. **Do not push the application
   code first**: missing metering RPCs intentionally stop model requests with 503.
2. After separate approval, install in order:
   `20261026_buffer_connections.sql` → `20261026_buffer_deliveries.sql` →
   `20261026_buffer_data_rights.sql`. Run all three matching audits (8/8/5
   PASS), including complete deletion coverage, before enabling.
3. Register a third-party app in Buffer. Exact production redirect:
   `https://postbeacon.app/api/buffer/callback`. Verify app access and X/LinkedIn
   channel eligibility/plan limits. HTTPS localhost is required for a dev callback;
   production rejects arbitrary redirect destinations.
4. Set server-only `BUFFER_CLIENT_ID`, `BUFFER_CLIENT_SECRET`,
   `BUFFER_REDIRECT_URI`, `BUFFER_TOKEN_ENCRYPTION_KEY` (base64 of 32 random
   bytes). Client secret/encryption key are Secret type. Keep separate non-prod
   apps/keys; never put them in `NEXT_PUBLIC_*`, chat, Git or project JSON.
   Keep the encryption key backed up securely; rotation makes old grants and
   account quota digests unreadable/unmatchable and needs a planned rollout.
5. Deploy with `BUFFER_PUBLISHING_ENABLED=false`. Verify manual publishing,
   disabled state, existing export/delete and no secret leakage first.
6. Only after separate enablement approval, turn the flag on and verify real
   OAuth, refresh, disconnect, two-account isolation, export and cancellation.
   An actual test post needs its **specific final copy, destination and time**
   approved at action time. No real post was authorized in this implementation.
7. Inspect natural scheduled delivery and a read-only sent receipt; if uncertain,
   stop and inspect Buffer. Never replace a timed-out request to make a test green.
