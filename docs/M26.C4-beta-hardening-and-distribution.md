2026-10-26. Implementation/acceptance record, not a claim of an autonomous CMO SLA.

## Product contract

The owner delegates bounded public research. Code checks permissions, budgets and
saved context; the model proposes a trial invitation. Results are persisted for
in-app review. A proposal, search hit, copied draft, scheduled post and confirmed
publication are different events. Only an actual recorded publication starts the
experiment clock; unknown outcomes never become zero or winning/losing evidence.

Established Next.js/Supabase/`lib/llm.ts` architecture is retained. No agent
framework, model, dependency, notification vendor or credential broker is changed
in this repair. Research authority does not grant external publishing authority.

## In-app delivery, not external push

The Agent inbox displays the latest five server tasks, saved receipts and actual
source/model attempt boundaries. Returning to the visible page triggers a bounded
read, never research or a model request. Active-job polling stays bounded and
aborts on account/project changes. Empty results remain reviewable receipts.

This is not an email/mobile push channel. Existing event emails remain separately
configured/opted-in; no new recipient is subscribed. The daily cron currently
inspects at most three missions once per UTC day. There is no exact-time guarantee,
infinite retry, scalable durable queue, 24-hour monitoring SLA or dollar-hard cap.

## User-confirmed next distribution design: Buffer

The owner chose **bring your own Buffer; X/LinkedIn; review then scheduled send**.
That selects a design, not permission to connect an account or publish a post.
The first integration is plain text plus an approved product link, one destination
per acceptance. Threads/media/bulk publishing are outside the initial adapter.

1. **Connect:** per-user OAuth Authorization Code + PKCE, one-time owner-bound
   state, exact callback URI, minimal scopes, explicit destination-account list.
   Tokens stay in a shared encrypted server store; no project JSON, browser,
   account export, model context or logs. Rotation must be serialized because a
   reused Buffer refresh token revokes the grant. A managed credential broker is
   an option only after Buffer support and tenant mapping are verified; not assumed.
2. **Review:** show exact account/channel, full native copy, verified claim issues,
   time zone and UTC scheduled instant. Server freezes a canonical payload hash,
   connection revision, owner/project, expiry and approval ID. Any content,
   account, media or time change invalidates it. Research consent cannot substitute.
3. **Reserve:** owner-composite foreign keys and a unique delivery idempotency key,
   per-user/account/global quotas, server-only dispatcher and kill switch. Each
   destination gets its own attempt/receipt. Never let an LLM issue arbitrary URLs,
   tokens or external-write payloads.
4. **Send:** one fixed Buffer adapter creates the approved scheduled item. A
   provider ID is `scheduled`, not `published`. An ambiguous timeout is `unknown`;
   reconcile before any retry. Do not claim exactly-once external side effects.
5. **Reconcile:** read the recorded provider item until sent/error/cancelled;
   owner-scoped receipts survive refresh. Only a verified sent lifecycle may
   create one canonical execution and start Measure. Partial batches remain partial.
6. **Revoke:** disconnect blocks new writes and invalidates unsent approvals.
   Explain any already accepted Buffer item that cannot be cancelled. Deleting
   PostBeacon history does not silently delete already published social content.

Feature remains default OFF until separate app registration/scopes, secret-store
choice, migration/RLS/export/delete/retention, platform policy and actual connected
test-account acceptance. Do not add a fake Connect/Publish button with no adapter.
Real test publication requires exact final copy, account and schedule approval.

Official Buffer documentation checked on 2026-10-26:

- [Third-party apps and rotating OAuth credentials](https://developers.buffer.com/guides/building-apps.html).
- [Scheduling, scheduled/sent/error states and app-client metrics limits](https://developers.buffer.com/guides/posts-and-scheduling.html).

Buffer currently describes X/LinkedIn support and custom UTC scheduling; actual
app access, user channel eligibility and current plan limits must be verified at
connection time. Third-party OAuth metrics must not be promised merely because
personal-key metrics are documented.

## Installation / release gates

1. Full offline gates, isolated PostgreSQL attack/concurrency/migration scenarios
   and independent final diff review; retain exact failures and remaining limits.
2. Separate production approval: install `20261026_workspace_ownership.sql`, run
   `audit-workspace-ownership.sql`; then `20261026_atomic_usage.sql`, run
   `audit-usage.sql`. Run existing base/Agent/mission audits too. No fresh base
   schema overwrite and no manual data cleanup to turn FAIL into PASS.
3. Only after the new RPC audit passes, release application code. Missing RPCs
   intentionally cause 503 before model spend, so deployment order is mandatory.
4. Desktop/mobile browser checks: no-source receipts, explicit source/review
   gates, first-trial state, saved tasks, cancellation/return-to-page continuity.
5. Fresh public/synthetic live research only within a new exact call allowance;
   pause the QA mission afterwards. No social publication or private inputs.
6. Natural scheduled run, real expiry and second-real-account acceptance remain
   separate evidence gates. Retention/product effectiveness needs real beta usage,
   not simulated activity or more generated posts.

## Explicit pre-billing blockers

Billing remains hidden/off. Atomic daily counts do not implement a successful-only
free-launch reservation/finalization/refund lifecycle across simultaneous Generate
requests. The existing billing webhook records idempotency before plan mutation;
plan mutation + event deduplication need one transaction before payment enablement.
Do not activate Polar or claim paid-plan concurrency acceptance in this repair.
