# M26.C2.1 — Assisted distribution and approved publishing plan

Status: planning plus a local assisted-handoff slice; not a production publishing integration.
Official platform documentation checked on **2026-10-24**. Permissions, pricing, quotas and
API availability must be checked again before implementation or purchase.

## What is actually available

- C.2.0 research-task code is released, but production Agent execution remains deliberately
  **OFF**. Production SQL installation, enablement and real-account/provider acceptance
  remain separate gates.
- This round's local slice prepares **one X post** in the platform's composer where
  supported, with Copy + Open as the manual fallback. Local acceptance is recorded below;
  this document does not claim that the slice has shipped or that prefill always works.
- Opening a composer is not posting. No external callback is assumed to prove publication.
  The user must publish on the platform and explicitly record the result in PostBeacon.
- No production SQL, environment setting, account connection, real publishing API request
  or social post was performed for this plan. Reading official documentation is not API
  integration acceptance.

The current **no-auto-posting** product contract remains in force. A future, separately
approved API-publishing feature would be a deliberate contract change, not an incidental
extension of research-task permissions.

## Product outcome: one useful distribution experiment

The CMO objective is not to maximize the number of destinations receiving the same text.
It is to help the founder get a real person to try one specific product task, capture the
response, and start a better second experiment.

The proposed sequence is:

1. Choose an audience, venue and concrete trial task from verified product facts.
2. Prepare a native draft with one clear request and pass the existing Truth Gate.
3. Show exactly where the user will publish and what manual action remains.
4. Record an actual publication, not an opened editor or scheduled queue entry.
5. Collect the goal-relevant result at the agreed window; missing data stays unknown.
6. Recommend and confirm the second experiment using the observed result.

CMO success should be assessed through time to a valid first publish, qualified trial
conversations, completed measurement, and willingness to start a second experiment.
Delivery counts alone are not evidence of acquisition, activation or retention.

## Delivery phases

- X: single-post prefill where it works, with explicit Copy + Open fallback.
- Other destinations: clearly labeled manual publishing; do not imply full text/media
  prefill when the platform only supports a URL share or a generic composer.
- Reuse the existing draft, safety gates, publisher voice and manual Publish dialog.
- Do not start an experiment clock on Copy, Open, a popup closing, or a browser tab change.
- Multi-post threads and automatic media attachment are outside this slice.

X's legacy Web Intent documentation currently redirects to its developer overview.
Consequently, compositor behavior needs actual browser verification and a reliable manual
fallback; a remembered intent URL is not sufficient proof of current compatibility.

### Phase B — Buffer OAuth, X and LinkedIn only

Use Buffer as a candidate distribution adapter, not as a replacement for the evidence,
draft or learning systems. Its current official documentation describes third-party
OAuth 2.0 Authorization Code flow with PKCE and post creation/scheduling.

- Start with one connected account and one plain-text/link delivery.
- Add an explicitly selected X + LinkedIn batch only after single-delivery acceptance.
- Present each account and native variant separately before approval.
- The integration must discover supported connected channels; never advertise all 19
  catalog venues as API-publishable.
- A scheduled Buffer post is **scheduled**, not **published**. Retain the Buffer ID and
  reconcile lifecycle state before recording platform publication and starting Measure.
- Do not promise automatic metric import for third-party OAuth: current Buffer help
  distinguishes personal-key analytics permission from third-party App Client access.
- Avoid making experimental content-item/draft endpoints a required core dependency.

Buffer's API is available on current plans including Free, but plan limits, connected
channels, queue capacity and media constraints still apply. This is not a guarantee of
free unlimited publishing or of permanent API terms.

### Phase C — DEV.to draft adapter

DEV's Forem API supports authenticated article creation with `published: false`. A
candidate narrow integration is **Create DEV draft**, followed by platform-side review
of formatting, attribution, canonical URL and AI disclosure before publication.

- Do not describe draft creation as publication.
- A user's personal API key is a sensitive credential; it must not be requested through
  a chat, stored in project JSON, or exposed to the model/browser.
- Verify current API and disclosure-field support before claiming API-complete publishing.

### Reddit — Keep manual

Reddit's technical submit endpoint does not imply application permission. Current policy
requires explicit API access approval and written approval/agreement for commercial uses.
A free beta is not sufficient evidence that a SaaS use case is non-commercial.

Keep user-controlled copy/open publishing and community-rule review. Do not add automated
comments, unsolicited private messages, bulk subreddit submissions, or a scraper as a
workaround for unavailable API permission.

## Approval and execution architecture

Keep the research-task worker separate from any external-write adapter. An opportunity
receipt or a queued experiment is not permission to publish. Models may propose content
and destinations; the server must enforce authorization and adapter capabilities.

### Immutable approval snapshot

Before a publishing request, show and bind an approval to:

- the authenticated PostBeacon owner and saved project;
- the provider connection and exact destination account/channel;
- the complete approved body and platform-specific variant;
- ordered media identities, content digests, alt text and validated delivery references;
- immediate or scheduled execution, including an unambiguous timezone/UTC instant;
- an approval identifier, canonical payload hash and expiry.

Editing account, body, media or time invalidates the approval. A research-text instruction,
old confirmation, a model tool request, or a newly reconnected account cannot reuse it.
The server independently runs deterministic safety/platform limits against the frozen
payload immediately before reserving a delivery. An expired approval requires review
again; the model must not silently regenerate content under an existing approval.

### Per-delivery ledger and honest partial results

One approved batch has independent deliveries, each with its own stable identifier,
idempotency key, approved hash, reservation, attempt state and provider receipt.

Suggested distinctions: `approved`, `scheduled`, `sending`, `published`, `failed`,
`unknown`, `cancelled`. Manual handoff remains a separate provenance, not a fabricated API
receipt. In a multi-platform batch, one success does not make failed/unknown peers succeed.

- Use a database uniqueness/atomic claim boundary against double-clicks and concurrent
  workers. Provider-side idempotency must be verified, not assumed from a local key.
- A network timeout after a write might have reached the provider. Mark it **unknown**,
  reconcile by recorded provider ID/status where possible, and do not blindly retry.
- API queue acceptance proves only queue acceptance. Publication needs a real confirmed
  platform/provider lifecycle receipt; retain its observed timestamp and source.
- Scheduling, delivery, cancellation and measurement are distinct states. A cancelled
  worker cannot guarantee withdrawal of a write already accepted by the provider.
- Do not claim exactly-once external effects unless the complete provider protocol makes
  that guarantee. Local fencing alone is insufficient.

## Credentials, privacy and revocation

- Use OAuth for multi-user integrations, not a shared founder personal key. Prefer minimal
  required scopes and a user-selected account allowlist.
- Keep tokens encrypted server-side using managed secret/key controls; no plaintext
  credential in projects/meta, localStorage, account JSON exports, model context or logs.
- OAuth state/PKCE, owner-bound callbacks, allowlisted redirect URIs and connection
  ownership checks are required. Return only safe account labels/connection state to UI.
- Reconnects and token rotation require atomic credential handling. Buffer currently
  documents single-use refresh tokens; concurrent reuse can revoke the entire grant.
- Disconnect blocks future writes, revokes provider credentials where supported, clears
  stored secrets and invalidates unsent approvals. Explicitly report queued items that
  could not be cancelled or writes whose final status is unknown.
- Account deletion removes connection secrets and owner delivery data according to the
  agreed retention contract. It must not imply that deleting PostBeacon also deletes
  already published social posts. Remote deletion is a separate explicit action.
- Export non-secret connection/delivery audit records while excluding tokens and secret
  material. Extend inventory, retention and deletion acceptance before feature enablement.
- Disclose the additional processor, data fields sent, storage and deletion behavior.
  No credentials or private customer responses should be sent to the generation model.

## Rollout and budgets

Publishing needs its own server-side default-OFF feature gate, separate from research
execution. Begin with operator-approved test accounts and a one-destination allowlist;
then gradually admit explicitly opted-in beta users.

Enforce per-user/per-account/global action limits, queue limits, bounded media sizes and
an operator stop control before external writes. Display any user-incurred platform or
Buffer cost/plan requirement. A request-count ceiling is not an exact monetary budget;
prepaid credit requirements, URL pricing, media and provider charges need separate checks.

No browser scripting of social sites as an API workaround. No automatic trending-topic
spam, duplicate multi-account campaigns, unsolicited outreach, or autonomous replies.
Any later scheduled/autonomous mode needs a separate, scoped authorization contract and
policy assessment; publishing one approved batch does not grant indefinite campaign power.

## Acceptance order and required user decisions

1. Finish current Agent production SQL/audit and separately authorized research enablement;
   do not silently include either in an assisted-handoff release.
2. Verify current local Copy/Open and X prefill with desktop/mobile browsers, clipboard
   denial, popup blocking, long text and Truth Gate failures. Confirm no false Published
   or measured-result state. Publish only the explicitly authorized accepted code.
3. Confirm whether to change the no-auto-post contract for **approved API publishing**,
   and choose Buffer OAuth versus direct single-platform integration.
4. Ask the user to approve provider/app registration, scopes, test accounts, privacy changes,
   any subscriptions/credits, cost ceilings and the exact first real test post.
5. Implement and test the connection/approval/delivery ledger locally using fakes: expiry,
   content change, wrong account, cross-user requests, duplicate clicks, token revocation,
   partial batch failure, late callbacks and ambiguous write timeouts.
6. Audit required SQL and encrypted secret storage. Production installation and feature
   enablement each require their separately agreed authority.
7. Read-only test-account connection validation, then one separately authorized draft or
   actual publishing test. Do not substitute mocked receipts for live acceptance.
8. Verify real receipt reconciliation, refresh/recovery, export/delete/disconnect, and
   result-to-second-experiment continuity before expanding destinations or scheduling.

Unresolved decisions include whether users will bring their own Buffer account, accepted
social scopes, who pays platform costs, permitted account types, supported media, and
whether the initial integration stops at draft creation, scheduling, or immediate posting.
No app approval, pricing, quota or production integration is guaranteed by this plan.
