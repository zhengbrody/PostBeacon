# M27.1 — One weekly task (phase 1)

2026-11-16, updated 2026-11-26. On branch `m27.1-weekly-task`, open as PR #3. **Not
merged, not deployed, no production SQL.** One approved real model request was made (see
"Not verified"). Verification status is stated per item below.

## What the user sees

Today starts with a **This week's task** card.

1. **Needs a plan** — three inputs: the user pain, the success signal (prefilled from the
   saved Success Contract) and hours available (prefilled from the weekly time budget).
   Product facts and the growth goal are reused, not asked again.
2. **Needs your confirmation** — one proposal: type, title, reason, cited verified facts,
   smallest scope, acceptance scenarios, test requirements, assumptions, non-goals and
   unknowns. The founder can edit it, ask again, or write the task without the Agent.
3. **In development** — a copyable **Build Brief** for Codex / Claude Code / Cursor, plus
   progress notes (the founder's own log, never evidence).
4. **Needs verification** — a result for every acceptance scenario, what changed, what
   was observed, optional link.
5. **Verified by you** — only after step 4 is complete. The card says PostBeacon did not
   inspect the product or repository.

Closing a verified task or abandoning one moves a one-line record to a small history and
frees the slot for the next week.

## Shortest path (added 2026-11-26)

The same card also appears on the **Diagnose** step, right after analysis. A founder can
go URL → confirm facts and goal → weekly task → Build Brief without building the channel
strategy or generating any content. For a signed-in founder that is two model requests in
total (analysis, then one proposal); writing the task by hand needs only the analysis.

Proposal request budget (`WEEKLY_TASK_BUDGET`): at most 12 verified facts, 240 characters
per claim, 900 output tokens, lists of at most 4 short items. A test pins prompt plus data
under 6,500 characters (roughly 1.5k input tokens) even with a 60-fact ledger.

## Rules enforced by code (not by the model)

- The model returns a proposal only. `lib/weeklyTask.ts` owns every transition.
- Every accepted change bumps `revision`. Commands carry the revision they were issued
  against; a duplicate click, a second tab or a late response is refused and changes
  nothing.
- A proposal is bound to the task id, revision and exact product version
  (`researchContextKey`) captured **before** the request. If facts or the goal change
  afterwards, the proposal is discarded (while planning) or confirmation is blocked.
- A model "product improvement" must cite at least one verified fact. Otherwise the only
  valid kinds are "validate demand first" and "usability check first", and they must
  state what is unknown.
- The model has not read the repository. Agent text that names files, code paths or
  code symbols, or claims to have inspected code, refuses the **whole** proposal (never a
  silent trim) with its own message. Framework names ("Next.js") and web addresses are
  not file references. This is a heuristic behind the prompt, not proof. The Build Brief
  says PostBeacon has not read the repository; a founder may name their own files.
- `verified` requires a change summary, an observation, and **every** scenario marked
  passed. A failed scenario cannot verify. Filler, the same text in both boxes, and text
  mostly copied from the plan are refused. These wording checks stop obvious non-evidence;
  they cannot tell whether the founder's account is true.
- Cited fact claims are frozen at confirmation, so later ledger edits cannot rewrite a
  brief that was already handed to a coding agent.
- Stored tasks are normalized on load; a state the machine could not have produced
  (for example `verified` without evidence, or untouched agent text that breaks the agent
  rules) is downgraded, never trusted.
- Fictional demo tasks and their history never cross into a real project: they are
  dropped when a real product is analyzed from the demo and on any non-demo load.
- An in-flight planning request belongs to one task; abandoning the task aborts it.

## Persistence decision

No new table. The task lives in `workspace.weeklyTask` (+ `weeklyTaskHistory`, ≤20), i.e.
`projects.meta.workspace` for accounts and the local draft for signed-out use
(`DRAFT_SCHEMA_VERSION` 13). The existing structure is enough for phase 1 because:

- it already has owner-only RLS, account export, account deletion and the 30-day
  inactivity retention — the task inherits all four with no new policy;
- reload recovery comes from the existing autosave;
- version conflicts inside one client are handled by the task revision.

Known limit, accepted for phase 1: project saves are last-write-wins across devices, as
for all other workspace state. Two devices editing the same task at once can overwrite
each other. A dedicated table with a server-side revision check is the fix if phase 2
needs it; it would require a reviewed migration.

## Model boundary

`POST /api/weekly-task` (same-origin, signed-in owner required, existing daily metering,
`no-store`). One `generateJsonOnce` request, OpenAI only — DeepSeek needs its own consent
step, which this surface does not have. Sent to the model: product name and audience,
verified fact ids + claims, the growth goal and rule, the three inputs, banned claims.
Not sent: the full profile, unverified facts, drafts, experiments, account identifiers.
The task is excluded from Copilot requests.

The fictional demo never calls this route: its proposal is written by code, labelled
fictional, and not saved.

## Phase-2 seam (not implemented)

`WeeklyTask.linkedPlannedExperimentId` is reserved for turning a verified task into a
trial kit through the existing planned-experiment queue. Nothing reads or writes it yet.
No publishing system, PR generation or marketing automation was added.

## Independent review — what changed

Fixed: repo-claim guard false positives (framework names, URLs) and false negatives
(README/package.json, extension-less code paths, code symbols, "I've reviewed…"); demo task
and history leaking into a real project; abandon during planning leaving a false
"planning" state; evidence check bypassable by one character; "write it myself" refused
in the demo; agent rules not re-applied on load; progress notes without a revision check;
a stalled session lookup defeating the timeout; silent trimming of agent list items;
"names no files" over-claim; card region semantics. The stored product-version key is now
a short fingerprint instead of the whole profile and ledger.

Left as is, on purpose: the raw `<select>` and dismiss `<button>` follow existing
components (there is no shared primitive); the same-origin check and "quota reserved
before body validation" match every other spend route and were not changed here alone.
