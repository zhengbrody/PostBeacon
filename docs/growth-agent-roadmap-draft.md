## 2. 先修正确性，不扩大错误

### A. 没测量不能写成 0

证据：`components/app/results/OutcomePanel.tsx` 的 zero preset 会同时把
impressions、replies、clicks、signups、revenue 写成 0。
“没有收到回复”不能证明没有曝光、点击或收入。

改法：逐项区分 measured value / not measured / unavailable；
快捷入口只能设置用户明确确认的指标。空值不进入零值判断。

### B. 过早或缺失的结果不能污染记忆

证据：`hooks/launchFlowReducer.ts` 将 promising 也记为 winning，
并将 72h 的 no-signal 记为 losing，包括未测量的情况。
`lib/today.ts` 的后续建议和 variantDirection 也可能把“早期进展”解释为
“参与但未转化”，或把未知结果解释为“内容没打动人”。

改法：明确 valid / insufficient / invalidated；记忆使用
untested / early evidence / repeated evidence / conflicting evidence，
引用有效 Outcome，不依据一次早期结果断言角度或渠道输赢。
历史记录原样保留；不凭空重建缺失指标。

### C. 搜索到、能打开、适合发布是三件不同的事

证据：`lib/discovery.ts` 在存在搜索结果时，没有强制验证模型选出的 URL
属于返回的搜索结果集合；可访问链接也可能被标为 validated。

改法：强制来源成员校验，使用代码生成的来源 ID；分别展示
search-backed / reachable / content-read / rules-reviewed。
未读到内容或社区规则的来源不能显示为发布机会已核验。

### D. Share Kit 应服务用户自己的产品

证据：`lib/experimentContract.ts` 当前截图任务和配文主要介绍 PostBeacon
的实验流程；它是截图指导，不是生成好的截图或用户产品推广包。

改法：拆分“推广我的产品”和“分享我的构建过程”。默认前者：
用户痛点 → 产品实际操作 → 真实使用入口。素材来自用户产品或用户提供截图，
不虚构界面、客户、结果；配文遵守 publisher voice 和同一 Truth Gate。
未完成的 Share Kit 不能伪装成已经可发布的附件。

### E. 实验契约与修复对象要准确

证据：Experiment Contract 的 tested variable 固定为 Hook；Experiment
保存 venue、angle、hook、Success Contract，但没有完整正文/事实/受众版本快照。
修复请求也没有绑定不可变的草稿 revision；Diff 读取当前状态存在过期风险。

改法：选择 tested variable 与 held-constant 字段，明确哪些没有控制；
发布保存 fact/voice/draft/contract 版本；修复绑定 draft ID + revision，
过期提案要求重新确认，不能对错误版本 Apply。
不要把观察性的发布测试表述成能证明因果关系的严格 A/B 实验。

本组验收：新增缺失值、早期/无效结果、来源集合、品牌语气、旧提案冲突测试；
完整 CI 门禁；桌面与真实移动 viewport 的主路径；原有历史仍可加载。

## 3. Agent 的目标与边界

目标不是“帮用户更多地发帖”，而是：
让正确的人理解一个明确用途，进入产品，完成一次真实任务，并愿意再次使用。

建议首批用户：已经有可运行产品或 Demo、缺少第一批试用者的独立开发者。
建议首版聚焦一个产品、一个人群、一个使用场景和一个实验；
先围绕获得试用与反馈，不开启自动投放、收费运营或无人值守传播。

价值路径：

`需求触发 → 一条有来源的机会 → 一个可操作演示 → 人工发布/邀请 → 实际试用 → 反馈 → 下一实验`

权限：允许读取用户提供或经授权的资料、研究允许访问的来源、准备内容、
提出计划；保存实验/变更必须确认。禁止自动发帖、回复、私信、买量、
创建外部账号或冒充用户。只读也受平台数据访问许可和费用限制。

## 4. 一次完整使用方式

1. 用户选择“本周让谁完成什么任务”，而不是仅选择推广平台。
   例如：让关注组合风险的投资者试一次假设情景，并告诉作者哪里难懂。
   这只是 MindMarket 的候选演示场景，具体功能必须重新取证确认。
2. Agent 对照产品证据与约束，提出最多三张机会卡。
   每张显示原始来源、可核实发布时间、需求摘录、匹配理由、规则检查、
   建议行动和未知项。找不到机会时明确说明；用户可提供来源，不编造热度。
3. 用户选一张；Agent 准备一套小而完整的试用材料：
   一条场景化文案、真实使用入口、三张产品截图指导/用户附件、
   三步体验说明、一个具体反馈问题。
4. 用户编辑并确认，手动发布或邀请；“已发布”只记录用户报告，
   不等同于 PostBeacon 已验证外部内容实际上线。
5. 到期只收集需要的证据：平台参与数据、聚合产品任务完成数、匿名化反馈。
   平台曝光与站内任务完成分开；没有归因或平台数据时标为未知。
6. Agent 区分卡在触达、理解、首次使用还是产品体验，展示依据和不确定性。
   不用低曝光推断产品不好，也不把零注册直接归因于 CTA。
7. 用户确认一个下一实验；它立即进入持久队列与 Today，
   返回页面后仍能继续，不需要重新生成整套计划。

## 5. 页面与交互

主界面为 Today 的工作卡，不另造一套长报告。

- 待研究：目标、人群、场景、预算；按钮“寻找可验证机会”。
- 待选择：最多三张机会卡；按钮“准备这次试用”。
- 待确认：文案/截图/入口/规则/真实性门禁；可查看 Diff 与撤销。
- 待发布：Copy / Open / 记录发布；明确人工动作。
- 待测量：倒计时、数据来源、主信号、缺失/无效选项。
- 已学习：本次知道了什么、仍不知道什么、三个下一步选择。

三个选择：同渠道换一个变量、同场景换一个 venue、暂停此方向。
每次确认展示 Change Receipt：发生的真实状态变化、依据、下一项任务。
不能用没有依据的百分比“信心提升”制造效果；失败、取消、超时也应有可恢复卡片。
聊天面板作为解释/修改入口，不能成为唯一工作入口。

## 7. 工程实现方式

沿用现有边界：safeFetch/URL policy、facts、llm、contentSafety、
copilotActions、launchFlowReducer、Supabase owner-only RLS；不建旁路状态。

新增核心对象建议：

- `Opportunity`：来源 ID、允许访问状态、需求摘录、读取时间、规则证据与未知项。
- `EvidenceSnapshot`：发布时的产品事实/语气/草稿/契约版本引用。
- `PlannedExperiment`：目标、一个变量、来源、下一项动作、独立计划 ID。
- `AgentRun` / `AgentStep`：run 状态、预算、已执行步骤、输出引用、确认、失败原因。
- `AdoptionObservation`：用户提供的聚合任务完成数据、时间范围、来源、归因局限。

一个协调器调用有界工具，不先做多个自由聊天的 Agent。代码负责状态转移、
指标判断、权限与预算；模型负责提出有来源的行动和素材。
长任务分步入队执行，不在 Next.js 请求中无限循环。
必须有最大调用数/token/费用/时间、幂等键、取消、恢复、错误退避、
跨用户隔离以及 run 与 draft revision 冲突检查。

外部页面与评论始终是未可信数据，不可作为工具指令；
模型不得自行选任意 URL 工具/数据库写入/供应商接口。
服务端写入验证身份、资源所属用户、提案版本与确认范围。
Agent 自身内容不进入产品遥测；继续不存第三方用户画像或跨产品内容池。
OpenAI 为默认，DeepSeek 仅在已披露/获同意的范围内 fallback；不重新启用 Claude。

新增持久执行对象需要真实 SQL/RLS/migration/export/delete/retention 覆盖，
不再用 best-effort mirror 承担 Agent 的关键执行状态。
目前 30 天不活跃项目保留政策要在 UI 明示；长期记忆不能承诺永久保存。
任何延长保留期或跨用户匿名学习都需独立产品选择与明示同意，不随 Agent 偷偷增加。

## 8. 验证产品是否有效

找 5–10 位符合首版人群的真实 Beta 用户，持续观察至少两周；这是试验设计，
不是承诺增长。分别记录并展示分母：首次草稿、实际发布、获得一次有效产品
试用/反馈、首个有效学习闭环、7 天内启动与完成第二实验、用户流失原因。

PostBeacon 的留存与用户产品的激活是两个不同层级，不能混为一个指标。
更好的文案或更多发帖本身不代表有效。小样本只读方向，不声称统计显著。
历史已有 `/api/metrics` 能帮助看执行漏斗，但没有真实用户数据报告就不能
宣称黏性已验证，也没有证据把记忆规模称为现成数据护城河。
