# C.2.0 — visible, persistent growth research

2026-10-24, America/Los_Angeles. Implementation and local acceptance record, **not
production enablement or completion of the whole Growth Agent roadmap**.

## User story

Today → prepare one audience/task/three-step trial with public excerpts → explicitly
start → saved task → source receipts → at most one selected-provider request →
reviewable result → manually review → existing dual-confirm boundary → Today queue.
No automatic posting, replies, DMs, background prospecting or invented product usage.

The Agent entry is now above the normal Today workbench. Old plans without a Success
Contract show **Complete experiment setup**, not a silently missing feature. Unsaved
plans show **Save project first**. A deployment with tasks disabled says so; preparing
a form is not execution. Availability reads do not claim that setup is disabled
before the first server response arrives.

## Architecture

- `lib/agentRuns.ts`: owner-visible projection and honest state descriptions; never
  exposes worker leases or a fictional percentage.
- `lib/agentRunServer.ts`: saved-project owner/context verification, atomic reservation,
  fenced worker transitions and existing C.1 orchestration. No new SDK/model/vendor.
- `/api/agent-runs`: authenticated, same-origin, bounded commands and latest-five reads;
  server-only `AGENT_RUNS_ENABLED=true` required. Storage/config errors fail closed.
- `hooks/useGrowthAgent.ts`: owner/project-scoped reads and commands, abort/discard on
  identity changes, bounded read-only polling, same request ID after a network error.
  It is not a parallel copy of plan state. Task results enter the plan reducer only
  on explicit **Review research**, and only with matching current product context.
- `OpportunityWorkbench` reuses existing material/rules/truth review. A completed job
  does not automatically add a draft, claim venue permission or queue an experiment.
- `after()` starts a request-backed worker after returning its durable reservation.
  The task row is authoritative; neither React state nor the best-effort workspace
  mirrors are used as the job ledger. See [Next 15 after](https://nextjs.org/docs/15/app/api-reference/functions/after).

This is **not an always-on scheduler**. A killed request can leave a queued/expired
task. The UI shows the saved state and permits explicit pre-model recovery, rather
than claiming continuous execution. A separate queue/Workflow-based scheduler remains
a later decision; no new hosted service or runtime framework was silently introduced.

## At-most-once model boundary and limits

Database row locks and a server-only transition RPC allow one worker lease. Source
checking may be explicitly resumed once before a model attempt, with a fresh lease
fencing the old worker. The run has a ten-minute overall deadline and each worker
lease lasts 55 seconds, within the route's 60-second limit.

Immediately before calling the existing `generateJsonOnce`, the worker atomically
marks `model_attempted`. Cancellation or a lost/expired lease prevents that transition.
Once marked, no worker can repeat it, even if the provider outcome is unknown. The
marker means **request reserved**, not proof that the provider received or completed it.
No SDK retry, provider fallback or paid JSON repair is added to this research path.
Cancellation fences late completion but cannot retract a request already sent.

Hard reservations apply to every plan: **10 tasks per user and 100 shared tasks per
UTC day**, at most one model request per task. Existing C.1 input/output limits remain
24,000 serialized user-input characters, 2,600 output tokens and 20s model timeout;
at most three explicit sources use the existing SSRF-safe fetch. Reservations are not
refunded on cancellation/failure, and project deletion cannot reset them. These are
atomic request allowances, **not precise dollar budgets or limits on every legacy AI
endpoint**. Absolute financial accounting and autonomous source discovery are not delivered.

DeepSeek requires a per-task acknowledgement; editing task inputs clears the checkbox.
Claude remains unavailable for this path. The existing OpenAI/DeepSeek model IDs and
other routes' provider behavior are unchanged.

## Data/security/privacy

Migration `supabase/migrations/20261025_agent_runs.sql` is additive and transactional:

- Owner-readable, server-written `agent_runs`; `(project_id,user_id)` composite FK
  prevents jobs pointing at another owner's project, even under a service-role write.
- Owner-readable/server-written `agent_daily_usage`; closed, identity-free
  `agent_daily_totals`. The global row serializes reservations, including first use.
- A server-written `entitlements.agent_data_initialized` marker is set in the same
  reservation transaction and backfilled on installation. It does not alter billing.
- Locked reserve/transition RPCs use invoker security; anon/authenticated cannot
  invoke them or write the task/usage tables. Browser payloads cannot set leases,
  job phases, provider outputs or completed state. See [Supabase function privileges](https://supabase.com/docs/guides/database/functions).
- Account export includes full owned task snapshots and daily owner counters. Before
  installation, missing optional tables yield empty data only for accounts without
  the initialization marker. If a marked account's table/cache becomes unreadable,
  export fails rather than silently omitting history. This distinguishes
  [PostgREST table-not-found errors](https://supabase.com/docs/guides/api/rest/postgrest-error-codes)
  from proof that a user never had Agent data.
- Project deletion/retention cascades task content. Account deletion includes task
  rows and owner counters; global counts have no identities and are not reset.
  The base schema's delete RPC also preserves optional Agent cleanup on rerun.
- Independent daily counters follow the operator retention sweep (currently intended
  30 days). Missing pre-install tables are reported as unavailable, not as deleted;
  real cleanup errors do not produce a successful-sweep claim.
- Public privacy inventory now discloses frozen input snapshots/excerpts, task state,
  output and daily reservations. No content or identity enters product telemetry.

The old campaigns/experiments/outcomes/tasks parent ownership and cross-device plan
last-writer-wins concerns remain separate. These new jobs do not depend on those
mirror relationships. This work does not claim that general project-save CAS,
whole-app two-account cloud QA or full relational remediation has been completed.

## Local acceptance

Run normal gates and the isolated database exercise:

```bash
npm run typecheck
npm run lint
npm run format:check
npm test
npm run build
npm run test:agent-db
```

The database exercise requires local PostgreSQL binaries (`initdb`, `pg_ctl`, `psql`).
It creates a fresh temporary cluster with a private Unix socket, no TCP listener,
simulated Supabase auth roles, and disposable fictional identities. It never reads
`.env`, accepts a database URL, connects to production or calls a model; it stops and
removes only its own temporary cluster. It checks migration reruns, the eight-row
installation audit, concurrent duplicate reservations, one worker/model reservation,
bounded pre-model resume, stale leases, user/global caps, cross-owner RLS/FK, server-only
commands, cancellation, project/auth cascades and deletion-resistant quota accounting.
This is real local PostgreSQL behavior, **not production Supabase/GoTrue acceptance**.

Offline route/worker/hook/UI tests additionally cover flag/auth/origin failures,
saved-context conflicts, explicit DeepSeek consent, no model work before durable
reservation, network idempotency, account-switch stale responses, legacy setup entry,
skipped-model labels, export completeness and retention errors. Browser QA found
unrelated loading falsely announcing a new draft; the workbench now checks actual
content changes, with a failing-scenario regression rather than a timer-based claim.

## Production enablement — deliberate, not automatic

1. Obtain release approval and deploy reviewed code with `AGENT_RUNS_ENABLED` absent
   or `false`. The new top-level UI is visible, but tasks truthfully remain disabled.
2. In the existing PostBeacon Supabase project's SQL editor, run the **entire**
   `supabase/migrations/20261025_agent_runs.sql`. It adds three tables, a marker column,
   composite-owner FK/index and server-only RPCs, and replaces the deletion RPC.
   Review these changes; do not paste service-role keys into a query or chat.
3. Run `supabase/audit-agent-runs.sql`. All **8** rows must say PASS. The original
   audit is still necessary for the old workspace; neither audit proves live behavior.
4. Only after confirming schema and account acceptance, set server-only Vercel
   `AGENT_RUNS_ENABLED=true` for Production and redeploy. Do not add `NEXT_PUBLIC_` or
   copy service-role credentials into Preview/browser code.
5. Use dedicated approved beta QA accounts/project: start one bounded OpenAI task,
   observe/reload its real receipts, review/confirm once, save/refresh/export, verify
   second-account isolation, cancel/failure/lease recovery and existing-plan continuity.
   A separately selected DeepSeek test needs current data/destination consent.
6. If any boundary fails, turn the flag off; preserve/export existing task data.
   Do not drop task tables to hide a failed acceptance or reset quotas.

No production SQL, environment setting, paid invocation or real account mutation
was performed by the local implementation. Production enablement, fresh migrated-SDK
provider acceptance, authentic product trials and first-to-second-loop retention remain
pending. This slice must not be announced as an autonomous Growth Agent or all of C.2.
